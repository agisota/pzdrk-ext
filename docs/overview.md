# Rox Discovery — project overview

## What it is

An AI-assisted Chromium Manifest V3 page-analysis extension. The **loadable extension in the repository root** is vanilla JavaScript/CSS (`manifest.json`, version 6.4.0); a **separate experimental TypeScript/Vite extension** (`vite.config.ts`, version 7.0.0) coexists in `src/`. Do not combine their feature claims: they have different entry points, prompt sets and settings behavior. The files here contain no `.git` checkout; the existing `.github/workflows` are source files, not proof that CI/release ran for this copy.

**Data flow and privacy:** summary/dialogue send the current page, its summary and this workspace's conversation to the configured external provider, not browser history. Finished workspaces automatically save Markdown through the authenticated loopback bridge to `Brain/Rox Discovery/`; “В Obsidian” appears only after a real write acknowledgement. Telegram sends only on an explicit export/test action. HTML strips executable generated markup; PNG stitches the full workspace and both diagram views. The separate modular build still has its own optional hub path and is not a port of the root workspace.

**Public-source configuration:** API credentials and Telegram account values are intentionally empty in the published source. Configure them in extension Options or an ignored `local-overrides.json`; never commit that file or `.env` files. Publishing does not change credentials stored in the installed extension.

**Prompts:** see [the full named and dynamic prompt/instruction inventory](prompts.md). The root has 18 named prompts and 17 action defaults in the shared `prompt-defaults.js`; that file feeds both root content and the shared options editor, while Vite content retains a separate summary contract. Shared evidence rules distinguish supplied page text, verified external sources and unverified search leads; optional evidence/details are not fabricated. Direct summary uses the editable `summary`/`summaryJson` prompt, but long-page map-reduce uses its own chunk/repair/merge prompts and summary assembly, so those direct templates do not customize that path. Saving unrelated settings does not persist displayed action defaults as overrides; only intentional differences are saved.

**Selected model:** `qwen/qwen3.8-27b` (Groq, Preview) is the default, and the user authorized switching the installed extension to it after the benchmark comparison. Other explicit saved model choices keep precedence over defaults. Compound is no longer the default; an explicit legacy Compound choice still receives its provider error without silently switching providers. Groq [documents Compound as decommissioned on September 21, 2026](https://console.groq.com/docs/compound/systems/compound).

**Installed vault bridge:** `server/obsidian-bridge.mjs`, `127.0.0.1:7421`, LaunchAgent `com.rox.discovery.obsidian-bridge`. Token stays private at `~/.config/pzdrk/obsidian-bridge.token` and in extension local settings. Only the exact installed extension Origin and bearer token are accepted; notes are atomic, deterministic by sanitized source URL, and confined to the configured vault. This service is separate from the optional modular hub on port 7420.

## Default configuration and its safety boundary

`shared-defaults.json` packages user-provided Groq and Telegram credentials/settings for first-run defaults; this overview intentionally does not repeat credential values or recipient identifiers. Stored user settings may take precedence, while explicit empty/disabled settings must remain meaningful rather than silently restoring a service. An explicitly cleared Groq pool stays disabled even if a stale legacy key remains, and an unrelated settings Save does not revive it. The CI/release ZIP includes this settings file and the root runtime's `prompt-defaults.js`; Vite also packages its shared defaults and the prompt script. Any installer can extract the credentials. There is no security benefit from hiding input fields or moving constants between client files. Do not treat these as private secret storage or publish a build without accepting account/bot exposure.

Client-side service credentials remain in extension source/default configuration; audit and rotate them before public distribution. Broad browser permissions and all-page content access expand risk. No live AI or Telegram call is required to inspect these defaults.

## Separate Vite/TypeScript track

- `vite.config.ts` defines its own MV3 manifest and emits `dist/` via `bun run build`; `src/background/main.ts` handles provider initialization, a queued retry path for some hub sync failures, connection checks and Telegram actions. `src/content/main.ts` owns a separate summary prompt: it serializes page URL/title/body as untrusted quoted data, validates the returned JSON fields, and reports malformed replies instead of accepting an empty summary. On success, content directly POSTs the result to the optional local hub outside the worker queue; that POST does not check HTTP error status, network errors are only logged, and the summary is not rendered by the modular content page. The popup `src/popup/` shows provider/local-hub status and quick actions, but its translate/mindmap buttons send actions for which modular content registers no handler.
- The modular popup's “Summaries” counter currently shows the number of providers returned by `getKeyStats`, **not** a count of completed summaries (`src/popup/popup.ts:86–94`). Do not use it as a usage metric.
- `src/core/api-router/` implements selection/racing/fallback/batching and circuit-breaker behavior; `src/core/key-manager/` tracks key quota/latency/cooldown. `src/storage/milvus-client/` and `src/storage/obsidian-sync/` contain vector-store and note-sync implementations. The `server/index.ts` Fastify app exposes summaries, search, stats, `/health` and WebSocket on port 7420. Milvus connection failure is caught by `MilvusVectorStore.connect()` and reported as `false`; startup continues, and `/health` only returns a static status/version, so it can respond while Milvus is disconnected (`src/storage/milvus-client/index.ts:14–34`; `server/index.ts:29–39,44–47`). `docker-compose.milvus.yml` supplies the vector-store infrastructure. The imported Obsidian manager is never constructed/initialized (`server/index.ts:4–5,14–15`), so Obsidian sync is not active.
- The alternate build is **not a complete port** of the root UI: it reuses root `options.html`/`options.js` (including saved-artifact and tracker controls that its background does not implement), while modular content handles a smaller message set. The root options editor saves personal Groq keys as `groqApiKeys`; modular content and background resolve nested `apiKeys.groq` first, then root `groqApiKeys`, then a nonempty legacy `groqApiKey`, then packaged defaults. An explicitly saved empty pool at either priority level disables fallback. The modular manifest has no DNR rules; the root manifest separately loads the static blocklist. `server/index.ts` has placeholder summary reads, and `generateEmbedding` returns random vectors, so semantic-search accuracy or durable summary-list claims must not be made.

## Build, tests, and delivery

- Root MV3: load the repository root as an unpacked extension in Chromium; there is no root build step. Vite: run `bun install` and `bun run build`, then load `dist/` as a different unpacked extension. `bun run typecheck`, `bun run lint` (modular `src/` only), and `bun run test` target the Vite TypeScript project; Vitest also contains focused root-runtime regression coverage. The root `npx eslint *.js` glob is ignored by `.eslintrc.json` and is not meaningful root lint coverage.
- The tag-triggered release workflow applies in its corresponding GitHub checkout. This working copy has no Git metadata; do not tag or push from it, and no release was made here.

## Known design and operational cautions

1. Public client-side defaults expose Groq and Telegram credentials to everyone who installs or inspects the extension; quota abuse, impersonation and unsolicited bot access are possible. Host keys behind authenticated, quota-controlled infrastructure if that exposure is unacceptable.
2. The optional local hub binds `0.0.0.0:7420` and enables permissive CORS (`server/index.ts:19–24,37–39`); it is not a secure multiuser credential proxy. Milvus failure does not prevent its weak `/health` response, although Milvus-backed routes cannot provide normal service while disconnected (`server/index.ts:44–47,75–97`; `src/storage/milvus-client/index.ts:14–34`). Search uses placeholder embeddings, and the Obsidian manager is not initialized.
3. Root content sends page data to its configured external AI provider; local artifact/cache storage does not make that provider-bound content private. Telegram transmission is a separate explicit export/test action. Broad browser permissions and all-page content access expand risk; no live AI or Telegram call is required to inspect the defaults.
4. Follow executable manifests and runtime code rather than stale copied guidance. The root and Vite extension are separate products; changes and prompt/settings behavior do not automatically transfer between them.
